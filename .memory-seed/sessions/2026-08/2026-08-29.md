### Summary

- Fixed the root cause the independent replication run measured: `session-log-check.py`'s only
  trigger was a 15-minute staleness clock, which could not have fired even once in a 13-minute
  run regardless of correctness. Added a content-based git-diff trigger, refined per JNL's three
  requirements (exclude the session log's own paths, don't re-fire on an already-covered
  uncommitted diff, baseline off the last logged entry rather than session start).

### Decisions

#### D1 - Add a git-diff fingerprint trigger alongside the existing time-based staleness check

- D: `.memory-seed/hooks/session-log-check.py` (and its seed twin) now computes a SHA-256
  fingerprint of everything `git status --porcelain` considers dirty, excluding
  `.memory-seed/sessions/**` and the hook's own state dotfiles, and compares it against a
  baseline stored in `.memory-seed/.session-log-check-state`. The baseline resets to the current
  fingerprint only when a new entry has appeared since the last check (`entry_advanced`); on
  every other check it is carried forward unchanged, so an already-logged-but-uncommitted diff
  never re-fires and only genuinely new dirtiness (a new file, or further edits to an
  already-dirty one, since the fingerprint hashes content, not just paths) trips the reminder.
  Fires the existing `SESSION LOG REMINDER` message (new wording variant: "detected from git,
  independent of elapsed time") whenever `is_stale OR dirty_since_baseline`, sharing one
  escalation counter with the existing time-based check.
- R: JNL identified the mechanism (a git-diff based trigger, since git already sees every file
  touched in a turn) after I traced the actual seeding-run timestamps and found the existing
  15-minute clock structurally could not have caught the failure: the 2026-08-27 replication's
  entire 10-session run spanned 13 minutes end to end, so no gap between any two logged entries
  ever approached 15 minutes, independent of whether the hook executed correctly every time. JNL
  then refined the design across two follow-up messages: (1) a diff inside the session log itself
  must not count as unlogged work, since writing the entry IS the git change and would otherwise
  make the hook fire on its own output; (2) an already-implemented-but-uncommitted change already
  covered by a session entry must not re-trigger on the next check - the comparison must be
  against the previous baseline (state as of the last logged entry), not the accumulation of
  everything dirty since session start.
- A: Considered a file-PATH-list fingerprint (cheaper, no per-file content hashing) instead of a
  content hash - rejected because it cannot distinguish "this file is still dirty from before" (no
  new work) from "this file was dirty before AND has now been edited further" (new work): JNL's
  own recovered scenario for the fix implies "edited it, logged it, then came back and changed it
  again" must count as new work, which only a content-based fingerprint catches. Considered
  raising or removing the 15-minute time trigger now that a content trigger exists - kept it
  unchanged: a real decision can be reached in conversation with zero file edits (e.g. "we decided
  X, implementation is future work"), which a git-diff check would never see, so the two triggers
  catch genuinely different failure modes and are combined with OR rather than one replacing the
  other.
- F: `.memory-seed/hooks/session-log-check.py`, `memory_seed/seed/.memory-seed/hooks/session-log-check.py`
  (kept byte-identical), `tests/test_session_log_ordering_hook.py` (6 new tests),
  `docs/2_Todo/memory-index-dry-run-plan.md` (root-cause-and-fix addendum on the Run 6 section).
- T: Manually simulated the exact S1->S2 scenario in a scratch git repo before writing formal
  tests (baseline absorbs a pre-existing dirty file; a new untracked file after a fresh entry
  fires via git, not time; re-checking the same uncommitted diff stays silent; re-editing an
  already-covered file re-fires; editing only the session log itself never self-triggers; the
  check fails open outside a git repo). Then added 6 automated tests covering the same scenarios
  plus the fail-open case; `tests/test_session_log_ordering_hook.py` - 20/20 passed (14 existing +
  6 new, no regressions). Full suite run pending at merge time.
