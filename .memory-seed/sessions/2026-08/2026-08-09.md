### Summary

- `memory_search` is how an agent decides WHICH memory to fetch, and the field it decides on was
  the first 280 characters of raw chunk text - which for an entry begins with the YAML metadata
  fence. 857 of 891 entry chunks led with it, it took a median 84% of the budget, and 124 previews
  never escaped it at all.
- Previews are now windowed on the terms that made the result rank. Same byte cost, entirely
  different content: on 40 sampled results, metadata-led 40/40 -> 0/40 and matched-term-bearing
  0/40 -> 40/40.

### Decisions

#### D1 - A preview is windowed on what matched, and every cut end says so

- D: `_selection_preview` replaces `_excerpt` at all three producers (`ranked_to_dict`,
  `rollup_entry_results`, `_evidence_record`). It strips a leading metadata fence, then windows
  around the earliest `matched_terms` hit with a short lead-in. An elided head carries `...`; an
  elided tail carries `[preview - call memory_get_chunk for the full entry]`. Decision granularity
  is untouched - `_decision_body` keeps its 2500 cap and exact marker.
- R: The fence is envelope, not prose: entry_id, user_initials, branch, topics and evolves are all
  already structured keys on the same result, so the preview was spending the reader's entire
  selection budget restating what it already had. `matched_terms` is computed by the ranker and
  already on the wire, so windowing costs no re-scoring - which is why the 2026-08-06 defect doc
  could list it as option 3 and defer it as "most work" while shipping the cheaper fix. That fix
  was right and cut 280-char serving from 45% to 6%; this is the residue it named. The marker
  asymmetry that started the thread is closed in the same change: `_decision_body` pointed at
  `memory_get_chunk` while `_excerpt` announced itself only as "...".
- A: Structural digest - decision names via `entry_body_decisions`, else Summary bullets. Rejected
  by JNL in favour of the window: a digest is query-blind, so it says what the entry contains but
  not why THIS result surfaced, which is the question a selection payload exists to answer.
- A: A total payload budget across the result set (the defect doc's option 2, its "likely answer").
  Rejected: the goal here is signal rather than volume, and a cross-result budget would make a
  result's content depend on its rank position, coupling this to ranking.
- F: `memory_seed/retrieval.py`, `tests/test_decision_retrieval.py`,
  `.memory-seed/skills/history_retrieval.md` + seed twin
- T: Corpus-wide assertion that no live entry chunk previews as metadata and none is empty, plus
  fence-stripping, term-windowing and marker tests. The three tight decision-excerpt assertions
  still hold (full `R:` line, no `...` in the last four characters, <= 2580).

#### D2 - The two agent-facing surfaces now agree on what an alias is

- D: `memory_search` results pass through `_project_search_payload`, which applies the existing
  `_project_chunk_payload` per result at the MCP boundary. `semantic_score` joins the keep-empty
  set, because a null there says the semantic pass did not run - the other half of the sentence
  `semantic_fallback_reason` starts.
- R: `memory_get_chunk` has dropped `path`/`date`/`source_file`/`entry_title` as aliases since it
  was written; `memory_search` shipped all 43 keys unprojected, so the two surfaces disagreed about
  what an alias is. Applied at the boundary rather than inside `search_memory` so the library shape
  stays stable for the experiments and tests that read it directly. The parity test needed updating
  and that is the part worth recording: `test_get_chunk_parity_with_mcp_tool` already established,
  on 2026-08-06, that parity holds THROUGH a declared projection - both surfaces run the same code
  and answer the same question, they do not serialise identically. Search had simply never been
  projected. The updated test additionally asserts the projection only ever prunes: every surviving
  key must be the service's, with an equal value.
- A: Also drop the scoring internals an agent cannot act on (`lexical_score`, `semantic_score`,
  `recency_multiplier`, `match_score`). Deferred by JNL to a future pass - they are the only
  debuggability MCP output has.
- F: `memory_seed/mcp_server.py`, `tests/test_retrieval.py`
- T: Parity holds through the projection across all four subtest configurations; 43 keys -> 31 on a
  sampled result, every one of them the service's own value.

### Summary

- One held a private copy of a production rule; the other hid the fact that it was structurally
  blind to what it was being used to check. Different faults, one shape of consequence.

### Decisions

#### D1 - A measurement asks the serialiser what it served; it never restates the rule

- D: `calibrate.py::served_chars` sums `ranked_to_dict(r)["excerpt"]` - the actual served field -
  instead of computing `min(len(chunk.text), DECISION_TEXT_LIMIT)` itself. The import of
  `DECISION_TEXT_LIMIT` goes with it, so there is nothing left to drift.
- R: The local copy was correct when written and silently wrong by the time anyone looked. The
  2026-08-09 preview change made it wrong in BOTH directions at once: entry chunks are now capped
  at 280 characters rather than 2500, so it overstated them by up to 2220 each, while capped
  decisions grew a 59-character marker it did not know about. Measured on one real query, top-8:
  the old formula said 8602 characters where the payload is 7651 - a 12% overstatement, live and
  unnoticed. A wrong measurement that crashes is a nuisance; one that keeps printing is a trap,
  because its output looks exactly like a correct one. Same family as the three copies of the ADR
  replay rules, which diverged twice before being collapsed, and as the file-touch hook's private
  420-character cap.
- A: Re-derive the rule locally but keep it in step with a test. Rejected - that is a fourth copy
  plus a guard for the copy, when calling the owner costs one line.
- F: `experiments/band-calibration/calibrate.py`
- T: `served_chars` over a live top-8 returns 7651, byte-identical to summing the served excerpts.

#### D2 - An instrument states what it cannot detect, before it states its result

- D: `answer_visible.py` prints a sensitivity line above the table: how many chunks are served
  WHOLE versus as a PREVIEW, and an explicit warning when the preview-served share is under a
  quarter of the store.
- R: The store is 11 decision chunks and 1 entry chunk. Decisions are served whole, so a change to
  preview construction can only move that single chunk - the metric was near-blind to exactly the
  change it was being used to verify. It returned 22/23 before and after, which is true and easy to
  misread as "the change did nothing" when it means "this test was not looking". The 2026-08-06
  defect doc hit the same wall and wrote it down - the dry-run "cannot measure a ranking change" -
  but that warning lived in prose while the script kept printing an unqualified number. Printing
  the limitation above the result is what makes it unmissable rather than merely recorded.
- A: Point the instrument at the real corpus so it becomes sensitive. Rejected here: the seeded
  store is the control the metric depends on, and swapping it changes what the number means.
  Declaring the blindness is honest and cheap; removing it is a different experiment.
- F: `experiments/memory-index-dryrun/answer_visible.py`
- T: Prints "near-blind to preview construction: only 1/12 chunks could move" above an unchanged
  22/23, which is the reading that was previously left to the reader to infer.

### Facts

- The rule the calibration script now calls lives in `retrieval.ranked_to_dict`, the same function

- Three instances of the same pattern are now recorded: replay rules (three copies, collapsed),

  written and none of them announced going stale.

### Decision

#### D1 - Topics gate membership, the ranker orders, and a second UNGATED pass catches what topics cannot see

- D: For each ADR with no decision ref, ESR runs `search_memory` over the ADR's title and decision
  text twice: once filtered to decisions sharing a topic with the ADR, once unfiltered. Gated hits
  show their shared topics; hits ranking well but absent from the gated set are marked STRAY. Top
  score is printed. Capped at 10 ADRs, fail-open, candidates only - attaching moves an ADR head.
- R: JNL's design, and both halves are load-bearing for measured reasons. The 2026-08-07 attachment
  review found topic overlap surfaces 5 of 5 approved picks out of ~1050 topiced decisions but ranks
  them at chance, so topics answer "could this be relevant" and `search_memory` answers "which
  first" - the same membership/ranking split `link audit` already uses. The ungated pass exists
  because a gated one can only return decisions inside the ADR's own topic family: a related
  decision attributed to a different area is invisible to it BY CONSTRUCTION, however relevant its
  text. That is a structural blind spot, not an unlikely edge case.
- A: Build a swarm for this, as JNL first suggested. Rejected on the count - 3 of 56 ADRs carry no
  decision, and a human reads three candidate lists faster than workers can be briefed. If a later
  run reports 20, the fan-out earns itself, and its job would be ranking by reading bodies, which is
  the half neither topics nor lexical search can do.
- F: `memory_seed/esr.py`
- T: Validated on the live corpus. The ungated pass immediately surfaced `ms-a8d0fc47` ("Publish
  2.6.0 to PyPI") at 30.3 for `adr_release_topology` - squarely the concern that ADR governs, and
  excluded by the topic gate. For `adr_runtime_discovery` both strays (18.5, 15.0) outrank the best
