### Summary

- Two merge-fuse fixes from the storylines review (R10, R11), implemented by an opus subagent
  against the approved plan and reviewed here. A fuse refusal now aborts its own half-started
  merge, and every apply-phase refusal message names WHICH side's copy failed validation.
- The change refines the merge-branch primitive's contract, so it is proposed as a revision on
  `adr_merge_branch_primitive` through the review gate in this same append - the head moves only
  if JNL accepts.

### Decisions

#### D1 - A fuse refusal aborts its own merge; genuine conflicts still wait for a human

- D: `session_merge_branch` and `session_prepare_pr_branch` auto-abort (`git merge --abort`) at
  every refusal exit that leaves no content conflicts - fuse validation refusals, unfusable
  paths, and git plumbing failures across six exits in each function, via one shared helper so
  CLI and MCP get identical behaviour. On success the result reports `merge_aborted=True` with
  "merge aborted automatically; nothing was committed" appended AFTER the refusal reason.
  Non-session content conflicts keep the leave-in-progress contract unchanged, and the
  `git commit failed` exit deliberately does not abort - the fuse succeeded there and the tree
  holds correctly fused work worth inspecting.
- R: A refusal's half-started merge has no value a human can extract - there are no conflict
  markers to resolve, only an outright rejection - and committing that state half-applies a
  changeset (nearly happened 2026-08-09). Conflicts are different in kind: they hold exactly the
  state a human needs. The prior "never abort" rule in `adr_merge_branch_primitive`'s orbit was
  written before refusals and conflicts were distinguished; this refines it rather than reversing
  it, which is why the ADR gets a revision proposal, not a silent drift.
- A: Blanket abort like the MCP handler - rejected by JNL: it would discard resolvable conflict
  state and flip the pinned conflicts-test contract.
- F: memory_seed/core.py, memory_seed/cli.py, memory_seed/mcp_server.py,
  tests/test_session_fuse_and_merge.py
- T: New chronology-refusal test asserts no MERGE_HEAD, clean tree, HEAD unmoved, and the abort
  line; the unrecognized-path refusal test flipped to expect auto-abort; the conflicts tests and
  MCP integrate tests unchanged and green. Full suite 1416 on the branch (this checkout collects
  the memory-trace suites; delta over baseline is exactly the three new tests).

#### D2 - Apply-phase refusals name the side whose copy was validated

- D: The twelve `_apply_session_fuse_plan` refusal messages carry side attribution in three
  families: "existing ... not chronological" names the BASE side (the committed content the merge
  reset the path to, with the base short-sha, and that the repair must land on base first);
  "already exists with different text" names both sides; "imported ... not chronological" names
  the source branch. The BASE claim is double-gated - only when the caller performed the
  base-reset AND the base commit actually holds the path - so a standalone `session fuse --apply`
  or a branch-new file is attributed to the working tree or branch instead, never falsely to base.
- R: The 2026-08-09 deadlock came from exactly this silence: "existing blocks are not
  chronological" reads as the branch's fault, the natural fix lands on the branch, and the fuse -
  which validates main's copy - refuses forever. The double gate exists because a blanket "it is
  base's fault" suffix would reproduce the same misdirection mirrored.
- F: memory_seed/core.py, tests/test_session_fuse_and_merge.py
- T: The chronology test asserts the BASE attribution text and sha;
  `test_standalone_fuse_apply_does_not_claim_the_base_side` pins the gate.
