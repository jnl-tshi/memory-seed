### Decision

- D: Reframe the variable schema by how each variable is enforced, and answer JNL's "does this flip a
  switch?" directly in the document's structure. Three classes: tooling-enforced (a command refuses -
  checkout_posture/worktree_decision via the worktree guard, integration_mode via integrate's pr decline,
  and PROPOSED merge_trigger via a refuse-without-override gate); config-toggled (governing_persona via
  _registry.yaml, skills_to_load via the trigger registry - both already exist, the gate only names them);
  advisory (write_intent/risk_tier/orchestration_level/version_state - judgments or facts with no switch).
- R: JNL's question exposed that the proposal as first written was advisory prose with no teeth - which is
  ironic for a proposal about making decisions non-ad-hoc. The honest answer is that enforceability is not
  uniform: some variables map onto switches that ALREADY exist (the worktree guard blocks root writes;
  integrate declines pr), some are config that already toggles behavior, and some are judgments no code can
  compute. Framing by enforcement class makes that spectrum the primary structure instead of hiding it, and
  it answers the user's question in the schema itself rather than in a footnote.
- A: The `merge_trigger` teeth are specified concretely and by analogy to two existing patterns rather than
  invented: an override flag that the tooling requires under `manual` and the agent is contractually barred
  from self-supplying - exactly the shape of `--allow-root-write` (root writes need a deliberate override)
  and `integration_mode: pr` (integrate declines outright). The reasoning that a CLI cannot tell an
  agent-initiated call from a user-initiated one, so "refuse to auto-run" needs a token representing user
  authorization, is stated so the mechanism is not mistaken for agent-discipline dressed up.
- A: Kept the advisory class honestly advisory. risk_tier and orchestration_level cannot be made switches
  because nothing can compute them; the document says so rather than pretending the gate enforces them.
  This is the same measure-do-not-overclaim discipline the rest of the session ran on.
- A: The §2 "set when" axis (session-stable vs intent-dependent) was preserved as a column rather than
  discarded - enforcement class is a second orthogonal axis, not a replacement. The two together are what
  make the schema legible: when is it established, and what happens if it is violated.

### Decision

- D: `merge_trigger` is unified to one meaning across both integration modes — "at a stable stopping
  point, does the agent auto-advance to the integration handoff, or hold?" — where the handoff is the
  merge into local main under `local-merge` and OPENING the pr under `pr`. Added a §5 "Modes available"
  matrix (integration_mode x merge_trigger) and narrowed §6.2 toward "own field".
- R: JNL's answer collapsed a cell I had called degenerate into a coherent one. The earlier draft claimed
  "in pr mode the trigger is arguably always manual" - now provably wrong: under pr, automatic auto-opens
  the PR while manual waits for the user to open it, so the axis is live under BOTH modes. That in turn
  answers §6.2 (facet vs own field) with evidence rather than preference: a variable meaningful under both
  integration modes is a real orthogonal field, not a local-merge sub-mode. I corrected the wrong line
  rather than leaving it standing next to the new matrix.
- A: The resolution surfaced a safety property worth stating explicitly, so I did: `automatic` never
  completes an irreversible or external step alone. Under pr it opens but never merges the PR (the merge
  stays the human reviewer's); under local-merge it merges locally but never pushes. So auto-advance is
  bounded to local, reversible actions in every mode - which is what makes an "automatic" default
  defensible at all.
- A: Generalised the teeth accordingly - the manual gate now refuses whichever command performs the
  handoff (`session merge-branch`/`memory_session_integrate` under local-merge, `session open-pr` under
  pr), not just the merge path, and the "don't auto-merge" shorthand became "don't auto-advance
  integration". The gate would otherwise have had a hole exactly in the pr case JNL just defined.
- A: The modes matrix makes the selectable surface explicit - three coherent cells plus the honest note
  that every other §4 variable is measured or derived, not a mode a user picks. The proposal's own
  contribution to "modes" is the single merge_trigger axis, and the matrix says so rather than implying a
  larger option space.
