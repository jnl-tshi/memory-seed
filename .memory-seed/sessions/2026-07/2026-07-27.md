### Summary

The verification command handed to worktree agents — `uv run --no-sync memory-seed docs check` — was
not running this repository's code at all. `--no-sync` leaves a worktree `.venv` empty (this worktree
had no `.venv` at all), so no console script exists there and `memory-seed` resolves through PATH to a
**globally installed, older** build at `C:\Users\johnn\.local\bin\memory-seed.EXE`. Its `docs check`
reported two phantom lane errors for `7_Replaced` and `4_Reference/trace-humanised-dashboard-references`
— both present in this tree's `docs_check.py` — and its `docs index` regenerated `docs/README.md`
dropping the `7_Replaced 29` lane count. Committing that would have landed a docs-index regression
attributable to nothing in the diff, which is the most plausible mechanism behind the recorded pattern
of merges landing on a red main.

`package_provenance()` now makes that invocation refuse instead of lying. The honest limit is stated
below and in `CONTRIBUTING.md`: it cannot catch the build that caused the incident.

### Decisions

#### D1 - Guard the mechanism, not the wording; the documented command was never the defect

- D: Implemented option (c) — `package_provenance()` in `core.py`, with the CLI exiting 2 and the MCP
  server warning on stderr — and deliberately did **not** do the broad option (b) rewrite of
  `memory-seed <cmd>` to `python -m memory_seed.cli <cmd>` across the control plane.
- R: The premise did not survive measurement. `uv run --no-sync memory-seed` appears **nowhere** in the
  repository: `grep` over `*.md`/`*.yml`/`*.toml`/`*.py` outside `sessions/` returns two hits for
  `uv run`, both `--no-project` measurement scripts in an ADR draft. The command came from harness and
  orchestration prompts, not from a file that could be fixed. What the repo does document is the bare
  `memory-seed <cmd>`, and that form is **correct** in the primary checkout (editable install) and for
  anyone who installed the published package — rewriting it to `python -m memory_seed.cli` would be
  actively wrong in the seed twins, which ship to consumer projects where `memory_seed` is not
  importable from cwd. A guard also defends against a command nobody wrote down, which is the class
  the incident actually belongs to.
  Option (a), dropping `--no-sync`, is the correct human remedy for the invocation and is documented as
  such, but it is not durable: there is no `uv.lock`, sixteen worktrees exist on OneDrive, and the repo
  cannot control how the next agent types its command.
- A: Broad (b) — rejected as a phantom target and harmful in the seed twins. (a) alone — rejected as
  not durable.
- F: `memory_seed/core.py`, `memory_seed/cli.py`, `memory_seed/mcp_server.py`
- T: `tests/test_package_provenance.py`

#### D2 - The predicate fires only inside a source checkout, so no consumer and no CI run is impugned

- D: The condition is: cwd or an ancestor holds `memory_seed/__init__.py`, **and** the imported
  package resolves outside that tree. Path comparison reuses the existing `_is_relative_to_casefold`.
  `version` and `help` stay runnable; `MEMORY_SEED_ALLOW_FOREIGN_PACKAGE=1` opens the gate for a
  deliberate cross-version run; falsey values (`0`/`false`/`no`/empty) do not.
- R: A seeded consumer project has no `memory_seed/` source tree, so the answer there is always
  "not foreign" and an ordinary `pipx`/`uvx`/`pip` install is never second-guessed. `verify.yml` does
  `pip install -e .`, which resolves the package **into** the checkout, so CI never trips it — a future
  switch to a non-editable install would, and that failure would look mysterious, so the docstring says
  so explicitly. `version`/`help` are exempt because they are how the mismatch gets diagnosed and
  neither reads nor writes the tree.
  The MCP server warns rather than refuses: a hard block at launch would take the harness's server down,
  and the server's own tools are how an agent would read the diagnosis.
- F: `memory_seed/core.py`, `CONTRIBUTING.md`
- T: `tests/test_package_provenance.py` (consumer-project case, casefold case, editable-install case)

#### D3 - Record what the guard cannot do rather than write it up as closed

- D: `CONTRIBUTING.md` and the CHANGELOG both state that a **pre-guard** global build has no such check
  compiled in, so the specific binary that caused the incident stays silent until the global install is
  refreshed. The remedy named there is `uv tool upgrade memory-seed` or `pip install -e .` into the
  worktree venv.
- R: A guard written in `memory_seed/` only executes when `memory_seed/` is what got loaded — which is
  exactly the case where nothing is wrong. Claiming the hazard is closed would be the same class of
  false confidence as the clean-looking local run this fixes. What the guard does close is the class
  going forward, and sibling variants (an installed 2.19 run against a 2.18 checkout).
  The demonstration follows from that: the guard cannot be shown firing through the stale binary, so
  `tests/test_package_provenance.py` simulates provenance by repointing `core.__file__`, and the
  evidence that the hazard is real is the separate observation that the global `memory-seed` on PATH is
  not in any `.venv` this worktree has.
- F: `CONTRIBUTING.md`, `CHANGELOG.md`

#### D4 - The propagation went to a twin-free file, plus one consumer-true line in the twinned skill

- D: The repo-specific rule (`python -X utf8 -m memory_seed.cli`, the guard, the env var, the CI note)
  went into `CONTRIBUTING.md`, which has no seed twin. `agent_collaboration.md` and its seed twin gained
  one bullet — "The tool you run is measured too, not just the tree" — worded generically about console
  scripts and empty worktree venvs, sitting directly under the existing "Worktree identity is measured,
  never declared".
- R: `test_integration_mode_contract_has_live_seed_parity` compares four live/seed pairs
  **byte-for-byte**, so a twinned file cannot hold repo-true text and consumer-true text at once;
  anything repo-specific has to live somewhere untwinned. The generic bullet earns its place in the
  shipped skill on its own merits — an empty worktree venv silently resolving a console script through
  PATH is a hazard for any seeded Python project, and it is the same epistemic rule one level down:
  the previous bullet says measure the tree, this one says measure the tool.
  `.github/workflows/verify.yml` needed **no** change: it has always invoked `python -m memory_seed.cli`.
  CI was never the gap — CI is what caught the red main.
- F: `CONTRIBUTING.md`, `.memory-seed/skills/agent_collaboration.md`,
  `memory_seed/seed/.memory-seed/skills/agent_collaboration.md`

### Follow-up

- The global `memory-seed` install is still pre-guard. Until it is refreshed, the exact invocation that
  caused the incident remains silent.
- Not built, flagged for JNL's call: the seeded `prepare-commit-msg` hook infrastructure could run
  `docs index --check` at commit time using an explicit `python -m memory_seed.cli` from the repo root.
  That would catch the *damage* (committing regenerated stale output) regardless of which binary the
  agent ran, which is strictly stronger than the guard — but it is outside the three options given.
