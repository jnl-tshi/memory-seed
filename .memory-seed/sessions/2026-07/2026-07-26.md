### Summary

Investigated NEXT_STEPS item 5 ("cross-session `branch:` contamination") against a synthetic-repository
matrix instead of by reasoning, and it split cleanly in two. The escalation premise turned out not to
hold for this repo, and the item's scope claim was overstated; one genuinely broken layout surfaced that
nobody had named, and that half is fixed.

Two corrections. `branch:` is the **only** git-derived field on an entry — `session_append_entry` makes
exactly one git call; every other key is caller-supplied, `read_local_user` is a file read, the entry id
hashes caller metadata, and diagram/topic/link sidecars carry no branch — so "affects every git-derived
field" shrinks to one field. And worktree isolation is a consequence of **`.memory-seed` being
committed**, not of worktrees: because it is tracked here, each worktree checks out its own copy, the
`resolve_runtime` walk-up stops there, and git reports that worktree's own HEAD. Today's parallel agents
record their branches correctly.

The matrix did expose a case with no concurrency in it at all: the same worktree layout with
`.memory-seed` gitignored. The walk-up escapes into the primary, so the entry is written into the
primary's memory dir *and* stamped with the primary's HEAD. Fixed by omission. What remains — two agents
in one checkout — is undecidable from git and is written up with options rather than guessed at.

### Decisions

#### D1 - Omit `branch:` when the memory dir belongs to another working tree

- D: When `rev-parse --show-toplevel` for the caller's directory differs from the same for
  `runtime.workspace_root`, omit `branch:` rather than stamping the enclosing checkout's HEAD. Extends the
  existing detached-HEAD / not-a-repository omission rule by one clause via a new `_auto_captured_branch`
  helper; no new flag, no advisory channel, no new machinery.
- R: This layout produces a wrong durable value with **no concurrency at all**, so the task's own
  principle decides it without a judgement call — a wrong `branch:` is append-only history, and refusing
  beats recording. Omission specifically, because *neither* HEAD is right there: the session is on the
  worktree's branch while the entry file lands in the primary's `.memory-seed` and will be committed on
  the primary's branch. The detector is exact rather than heuristic — the two toplevels agree in every
  layout that behaves correctly and disagree precisely when the write crosses trees — so it carries no
  false positives. Shipped rather than proposed because `memory-seed` is on PyPI: this repo tracks
  `.memory-seed` so the rule never fires here, but any downstream user who gitignores it gets silently
  wrong branches in every worktree.
- A: Also omits for a caller inside a submodule whose superproject owns the memory dir. Judged correct —
  the submodule's branch is not the superproject's, and the entry commits on the superproject's. Costs one
  extra `rev-parse` per append, which is a once-per-entry path, not a hot loop.
- F: `memory_seed/core.py` `_auto_captured_branch` plus the `session_append_entry` docstring;
  `tests/test_session_append.py::BranchProvenanceTests` pins the whole matrix. Full suite 743 passed;
  `links check` and `docs check` both OK.
- T: `.memory-seed` being tracked is load-bearing for worktree isolation and nothing states that anywhere
  — worth asserting in a test over this repo's own layout if it is ever to be relied on.

#### D2 - Leave the shared-checkout half to a maintainer decision rather than a heuristic

- D: Do not implement a warning for two agents sharing one checkout. Record the finding and four options
  in `docs/2_Todo/branch-field-provenance.md`, mark item 5 as needing JNL's decision, and recommend (not
  decide) option A plus D: document the existing `--branch`/`--no-branch` workaround, and have the agent
  harness pass `--branch` unconditionally.
- R: Two agents in one working tree have a genuinely identical HEAD, and an agent's session branch is
  never passed to the CLI — there is no state from which any code could recover it. The only implementable
  signal, "this repo has more than one worktree", would fire on every legitimate primary-checkout append
  here, which is now routine; that trains the warning to be ignored within a week. Inventing a heuristic
  the maintainer did not ask for would be guessing at a policy question, and the task was explicit that a
  judgement call belongs in a proposal.

### Decisions

#### D1 - Containment travels through a compound node, never a fifth edge kind

- D: An entry and its decision rows are filed under a synthetic `dgroup:{entry_id}` Cytoscape compound
  parent that holds **both** the anchor and its rows as children. The anchor is never the parent, and
  nothing is added to the edge set.
- R: The four edge kinds are **authored semantic claims** — forward-only, acyclic, dangling-ref
  validated — which is exactly why `intra-entry-decision-ref` is an authoring error: an entry and its
  own decisions are contemporaneous, so no forward-only claim between them can exist. Anchor↔row
  containment is derived and structural, so filing it as an edge would put a derived fact in a channel
  defined as authored claims and force every edge-kind consumer to learn an exclusion. JNL had already
  chosen this channel (option b) earlier on 2026-07-26; this implements it.
  Not the anchor as parent, for two reasons that are structural rather than aesthetic: a compound
  parent is **auto-positioned** from its children's bounding box, and this simulation writes every
  participant's position on every tick, so the two would fight; and a parent is **auto-sized**, so the
  entry would lose the circle/degree-size/topic-fill/authored-rim vocabulary the rest of the map reads
  in. As a child, the anchor keeps all of it.
- A: A fifth edge kind — rejected on the contract above. A leash force between anchor and row —
  rejected: it would move anchors, so turning rows on would rearrange a map the reader already knows.
  Anchor-as-parent — rejected on the auto-position/auto-size collision.
- F: `memory-trace/client/src/GraphWorkspace.tsx`, `memory-trace/client/src/App.tsx`,
  `memory-trace/client/src/SettingsMenu.tsx`, `memory-trace/client/src/api.ts`,
  `memory-trace/client/src/graphDecisionRows.ts`.

#### D2 - Rows are derived from their anchor, not simulation participants

- D: Decision rows are excluded from the d3 simulation. Their position is recomputed from their
  anchor's after every position write (a new `afterPaint` hook inside the paint batch, plus an explicit
  call on mount and on fixed-mode drags). Each row aims at the mean direction of its counterparts,
  falling back to a golden-angle fan slot, with a fixed-step rotation walk so two rows never coincide.
- R: This is what makes containment **true by construction** rather than enforced: a row cannot drift
  out of its group, no leash is needed, and — the property that matters most — turning rows ON moves no
  anchor at all, because a row exerts no force on anything. Counterparts resolve to the counterpart's
  **anchor**, never the counterpart row: anchors are simulation participants, so the position read is
  settled for the frame instead of being derived in the same pass, which makes the arrangement
  deterministic rather than order-dependent. The three call sites exist because paint is not the only
  way an anchor moves: a settled mount never ticks at all (alpha starts at 0), and a fixed-mode drag
  deliberately never wakes the loop.
- A: Let rows take part in the simulation and add a short strong link to the anchor — rejected: it
  makes rows push on everything else, which violates the "no anchor moves" property outright.
