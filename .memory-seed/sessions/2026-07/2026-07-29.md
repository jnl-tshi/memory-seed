### Summary

- Trace could previously only switch between git worktrees of the repo it launched into. JNL asked for
  the ability to point it at any folder on disk from inside the app, gated by the folder having a
  correctly-initialised `.memory-seed/`. That gate is the real `doctor()` check - the same one
  `memory-seed doctor` runs - not a lighter existence check invented for the occasion.

### Decisions

#### D1 - Opened folders join the SAME allowlist git worktrees use, so every existing endpoint serves them for free

- D: `create_app()` gained a process-lifetime `external_projects: dict[Path, dict]` registry alongside
  the existing `worktree_services`/`worktree_lock`. `worktree_entries()` now returns git worktrees plus
  `external_projects.values()`; `service_for()`'s allowlist (`known = {...for entry in worktree_entries()}`)
  was untouched, because it already derives from `worktree_entries()`. Registering a folder there is
  therefore the entire integration - `/api/v1/facets`, `/search`, `/graph`, `/trail`, all of it, work on an
  opened folder with zero further changes.
  Two new endpoints do the actual work: `GET /api/v1/browse?path=` walks the server's filesystem (cheap
  `.memory-seed` existence hint per row only, no `doctor()` per listing), and `POST /api/v1/projects?path=`
  is the real gate - runs `doctor(path)`, and on `.ok` registers the folder and returns a `WorktreeInfo`;
  on failure returns `{ok: false, issues: [...]}` as a normal 200, not an error - "not initialised yet" is
  an expected outcome the UI has to render, not a fault.
- R: The existing worktree allowlist was deliberately git-only ("only paths git reports as worktrees of
  this repo are ever served (no arbitrary-path reads)" - service.py's own comment). That invariant stays
  true for the git path; what changed is that a SECOND, independently-gated way to earn a spot in the same
  allowlist now exists, admitting exactly one folder at a time and only after `doctor()` passes. Reusing
  `doctor()` rather than a lighter check was a direct read of JNL's wording ("correctly initialised") -
  that phrase already has a precise meaning in this codebase (`missing == [] and version_mismatches == []
  and bootstrap_missing == []`), and a folder with SOME `.memory-seed/` files but not all of them is
  exactly the case worth catching, not waving through.
  Browsing and opening are two different requests on purpose: `doctor()` spawns git, scans the whole
  corpus for encoding issues and session-link integrity - fine for one user-initiated "Open" click, far
  too expensive to run on every row of a directory listing just to draw a picker.
- A: A lighter ad-hoc check (does `.memory-seed/` exist as a directory) - rejected: `resolve_runtime()` is
  exactly this and is explicitly a locator, not a validator (it never raises, and returns a `Runtime`
  pointing at a directory that may not exist). Using it alone would open folders doctor() would flag as
  broken. A brand-new mutable "current server root" - rejected: the existing per-request `?worktree=`
  pattern already generalises correctly to more paths; replacing it with a single global root would have
  been a bigger, riskier change for no benefit, and would have broken concurrent requests scoped to
  different worktrees.
- F: `memory_trace/service.py` (`browse_directory`, `validate_project_init`, `external_projects` registry,
  `v1_browse`, `v1_open_project`), `memory_trace/models.py` (`DirectoryEntry`, `BrowseResponse`,
  `OpenProjectResponse`), `tests/test_project_open.py` (new, 6 tests), `tests/test_openapi_contract_fixture.py`
  (+2 expected paths), `tests/contract/{openapi.v1.json,types.ts}` (regenerated).
- T: 216 Trace tests passing (1 pre-existing, unrelated failure confirmed via `git stash` to fail
  identically on unmodified main - a subprocess-spawned test that needs `memory_trace` pip-installed in
  this local venv, which it never has been; not something this change touched). Live: opened a real
  throwaway project built with `init_project()` - `doctor()` correctly refused it once (missing
  `index.md`/`policy.md`, the two BOOTSTRAP_GENERATED_FILES `init_project()` alone does not write) and
  accepted it once those were added; a bare uninitialised folder was refused with populated `issues` and
  never appeared in `/api/v1/worktrees`.

#### D2 - The picker is a modal folder browser reusing the worktree-switch choreography, not a new switching mechanism

- D: New `FolderPicker.tsx` (modelled on `DiagramViewer`'s backdrop/Escape/outside-click pattern): browses
  via `GET /api/v1/browse`, marks folders with a `.memory-seed/` with a `FolderCheck` icon (a hint, not a
  promise - opening can still be refused), and either row has its own "Open" or the current folder has
  "Open this folder". A refusal shows the actual `doctor()` issues inline rather than just failing.
  On success, `App.tsx`'s new `handleProjectOpened` refetches `/api/v1/worktrees` (so the new entry's
  label exists) and calls the EXISTING `chooseWorktree()` - the same full-state-reset, "train of thought"
  loading choreography a git-worktree pick already uses, given the label directly (a new `labelOverride`
  param) rather than via lookup, since the just-registered entry is not yet in React state at the moment
  `chooseWorktree` is invoked.
- R: The worktree-switch machinery (full app-state reset, scoped fetch via `?worktree=`, the loader) was
  already exactly the right shape for "now serving a different corpus" regardless of how that corpus was
  chosen - reusing it outright, rather than building a second switching path, is what makes an opened
  folder behave identically to a worktree everywhere else in the app (the picker in the "Project" pane,
  visible search, graph, trail - all of it already worktree-aware).
- A: A second, separate "active project" concept parallel to worktree - rejected as unnecessary
  duplication once D1 put opened folders in the same backend allowlist; the frontend mirroring that
  choice is the natural consequence, not a separate decision.
- F: `memory-trace/client/src/FolderPicker.tsx` (new), `api.ts` (`browseQuery`, `openProject` -
  deliberately bypass the `api<T>()` helper's automatic `?worktree=` scoping, since browsing/opening act
  on the server's filesystem and project registry, not the currently active corpus), `App.tsx`
  (`handleProjectOpened`, the "Open folder…" button, `chooseWorktree`'s new `labelOverride` param),
  `styles.css` (`.folder-picker-*`, `.open-folder-button`, a `.spin` keyframe this app did not have yet).
- T: 226 client tests passing (unchanged - no new pure-module logic to unit test; the new code is UI
  wiring, covered by the live check below), `tsc --noEmit` clean, `vite build` clean. Verified live end to
  end: built a real throwaway project under the home directory with `init_project()` plus the two
  bootstrap files, opened the picker, navigated into it, clicked "Open this folder" - the app switched to
  it (Trail showed exactly its one entry), and `/api/v1/worktrees` listed both `main (primary)` and the
  opened folder.

### Follow-up

- **A label wording bug was caught and fixed mid-verification, not left for later**: `api_worktrees()`'s
  existing `branch or f"{name} (detached)"` formula ran unchanged for external entries too, so the opened
  folder first showed as "trace-open-demo (detached)" - a git concept (detached HEAD) applied to something
  that was never a git worktree. Fixed by tagging registry entries `external: True` and skipping the
  "(detached)" suffix for those; re-verified live that the label now reads plain `trace-open-demo`.

  same picker. No "recent folders" list either. Both were left out as scope not asked for; either would be
  a small, contained addition to `external_projects` if wanted later (a small JSON file next to the cache
  root, read at `create_app()` time).
- `POST /api/v1/projects` takes `path` as a query parameter, not a JSON body - documented in the code
  itself as a workaround, not a preference: this module has `from __future__ import annotations` on, and a
  Pydantic model imported locally inside `create_app()` (the pattern every other model here already uses)
  cannot be resolved as a parameter TYPE ANNOTATION under that setting, because FastAPI can only
  re-resolve a stringified annotation against the function's module globals, not the enclosing closure. A
  `response_model=` kwarg doesn't hit this (eagerly evaluated, not stringified), which is why every
  existing v1 endpoint's local model import already worked and this one silently didn't, caught only by
  actually running the test rather than assumed.
